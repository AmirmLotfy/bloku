# Local popup-rule integration audit — 2 November 2026

## Finding and bounded change

The baseline rejected an otherwise parsed local `$popup` rule because the final SDK dynamic-conversion result included `UnsupportedModifierError: Network rule with explicitly enabled $popup modifier is not supported`. That error describes a DNR limitation. The pinned SDK also has a separate TSUrlFilter popup matching and tab-close path. Rejecting every dynamic conversion diagnostic made that existing path unavailable to local popup rules.

`B2/engine/conversion-diagnostics.ts` now recognizes only the precise pinned-converter popup diagnostic. Recognition requires an actual `UnsupportedModifierError`, an actual converter `Rule`, the SDK's local user-filter ID, a valid character offset at a source-line boundary, matching source rule text, and an explicit positive `popup` modifier. Only `popup`, `domain`, `to`, `third-party`, `match-case` and `important` modifiers may appear. Mixed resource/response modifiers remain fatal because the converter can report popup before reaching another unsupported capability in the same rule.

The adapter passes the full prepared local filter unchanged to the SDK. It excludes the recognized diagnostic from fatal **dynamic** errors only. All static errors, dynamic limitations/truncation, malformed rules, other unsupported conversion errors and API/quota failures retain the existing failure/rollback path. Focus/generated document rules cannot qualify. The complete expected DNR count, selected rulesets and static disabled-rule-ID checks remain in place. Policy security checks, SDK ownership of DNR, and transaction logic are unchanged. No global `window.open` interception or second rule writer is added.

## Observer and permission trace — read-only follow-up

The coordinator reported that the candidate accepts the local popup rule, but its first browser experiment was inconclusive: the before-rule popup positive control itself timed out, and the immediate window-reference closure check did not establish closure. This is not a native tab-closure pass. No permission or production source change is justified by that result alone.

The pinned SDK's complete relevant path is:

1. `TsWebExtension.innerStart` first awaits configuration, then initializes `RequestEvents`, starts `WebRequestApi` observers and starts the shared tabs observers (`index.mv3.js:6421–6441`). Successful configuration awaits `engineApi.startEngine` and retains the prepared user-filter content (`:6615–6645`, `:432–451`). User popup rules do not depend on `userScripts`, a popup-specific setting, or enabled declarative filtering logs; those controls do not gate this local-rule path.
2. `TabsApiCommon.start` subscribes to `tabs.onCreated`, `onRemoved` and `onUpdated`. A browser tab is accepted when its ID is numeric and not `TAB_ID_NONE`; no opener property or readable URL is required. `handleTabCreate` stores a context even when URL data is missing (`common/stealth-actions.js:1925`, `:2110–2184`).
3. `RequestEvents` registers observation-only `webRequest.onBeforeRequest` for `<all_urls>`; there is no blocking listener flag. It takes source context from `details.originUrl || details.initiator || ''`, falling back to the destination tab's recorded main/frame URL or the request URL. The computed source becomes `frameUrl` for matching. A scoped `domain=` popup rule therefore depends on the actual browser-provided request initiator, not necessarily the top-level website's hostname (`index.mv3.js:2226`, `:2268–2377`). An embedded frame opening a popup can supply its own origin.
4. `WebRequestApi.onBeforeRequest` maps the HTTP main-frame request to `RequestType.Document`, ensures a tab context exists, and calls TSUrlFilter with request URL, computed source URL and any document-level allowlist rule (`:5856–5979`). TSUrlFilter stores popup rules separately and returns the popup rule as its basic result when no higher-priority basic rule applies (`@adguard/tsurlfilter/dist/es/index.js:6016–6043`, `:6056–6113`).
5. `RequestBlockingApi.getBlockingResponse` first requires a basic result and returns early for allowlist rules. For a document request with a popup match, it calls `closeTab` only if `tabsApi.isNewPopupTab(tabId)` succeeds. `closeTab` invokes the stock `browser.tabs.remove(tabId)` operation; MV3's returned `cancel:true` is observational and is not the closing mechanism (`index.mv3.js:4223–4313`).
6. The stock MV3 new-popup predicate checks only whether stored `tab.info.url` is **undefined, empty or `about:blank`**; a missing tab context fails the predicate. It does not inspect `openerTabId` or tab age (`:773–782`). `onBeforeRequest` and `onBeforeNavigate` can each create a synthetic context with `url` equal to the target if `onCreated` has not populated the context first (`:5868–5870`, `:6108–6110`; `common/stealth-actions.js:2197–2224`). That creates a concrete, source-supported event-order sensitivity: a synthetic target URL would fail the new-popup predicate. Whether this happened in the coordinator's browser is still unobserved.
7. `onCreatedNavigationTarget` appears in the SDK's explanatory flow diagram, but the inspected MV3 implementation does not register that event as the popup-close trigger. The actual path above uses tabs creation/update plus webRequest. It is useful as an independent fixture observer because it identifies source and destination tabs.

Current production manifest permissions already include `webRequest`, `webNavigation` and all HTTP(S) host grants. [Chrome's Tabs API documentation](https://developer.chrome.com/docs/extensions/reference/api/tabs) says that the `tabs` permission grants access to sensitive tab properties, while host grants expose those properties for matching tabs; the namespace itself does not require `tabs`. Its `tabs.remove` method has no separate `tabs` permission requirement. Initial tab URLs may be unset at `onCreated`, independently of permission. Crucially, undefined URL already satisfies the SDK's new-popup predicate, so adding `tabs` to reveal `about:blank` has no demonstrated benefit. [Chrome's webRequest documentation](https://developer.chrome.com/docs/extensions/reference/api/webRequest) permits observation in MV3 with `webRequest` plus the relevant host grants; tab closure does not require `webRequestBlocking`. The existing `webNavigation` permission covers its [navigation events](https://developer.chrome.com/docs/extensions/reference/api/webNavigation). No additional capability is established as necessary by this trace.

### Smallest discriminating browser check

Keep the manifest and production source unchanged. In the fresh disposable browser profile, attach temporary worker-side listeners **before** a native button click. Record only the local fixture's `tabs.onCreated` (`id`, `url`, `pendingUrl`, `openerTabId`), `tabs.onUpdated` URL transitions, `tabs.onRemoved`, `webNavigation.onCreatedNavigationTarget` (`sourceTabId`, `sourceFrameId`, `tabId`, `url`) and `webRequest.onBeforeRequest` (`type`, `tabId`, `url`, `initiator`, `originUrl`). Record timestamps and detach those exact listeners after the bounded check. A server request alone cannot show whether a tab was immediately removed.

First obtain an observed created-and-still-open popup with **no** local popup rule, using a native user click on an ordinary HTTP fixture. Stop if this positive control fails. Repeat with only `||popup-target.test^$popup` (destination-specific, no source-domain condition), then the scoped variant. That isolates runtime closure from source-domain matching without global interception. If unscoped works and scoped fails, compare the recorded initiator with the rule's `domain`; an iframe source must be tested separately. If both fail despite an observed target main-frame request and accepted state, inspect SDK tab context and local-only `SendRequest`/`PopupBlocked` events through a disposable harness importing the SDK's public `tabsApi`, `defaultFilteringLog` and `FilteringEventType` exports. This can distinguish a source match from a failed new-popup predicate or rejected `tabs.remove`, without modifying the SDK or adding permission.

Treat `window.open`'s returned handle, `handle.closed`, popup UI visibility and frame screenshots as supplementary evidence. Require actual extension/browser tab creation/removal events for the closure claim. If the event-order predicate is the failure, record that stock-SDK limitation and stop widening this milestone; do not add a second DNR writer, patch global `window.open`, or add a broad permission to speculate around it.
